# admin-notifications Specification

## Purpose

Provide a single, consistent toast notification system for the admin dashboard so every create/update/delete flow surfaces a success toast and every failure surfaces an error toast, backed by one globally provided PrimeNG `MessageService` and one `<p-toast>`.

## Requirements

### Requirement: Single global MessageService provider

The admin application SHALL provide `MessageService` exactly once, globally, in `app.config.ts`. No component, directive, or feature route SHALL list `MessageService` in its own providers array.

#### Scenario: MessageService provided once globally

- **WHEN** the application bootstraps
- **THEN** `MessageService` is registered in `app.config.ts` providers exactly once

#### Scenario: No component-level MessageService providers

- **WHEN** any component, directive, or route declares a `providers` array
- **THEN** that array does not contain `MessageService`

### Requirement: Single p-toast in the root layout

The admin application SHALL render `<p-toast>` exactly once, in `AdminShellComponent` (the root layout shell used by every page). No other `<p-toast>` SHALL exist in the project. The toast SHALL use no `key` unless there is a documented reason and SHALL set `[baseZIndex]` high enough to render above `p-dialog`.

#### Scenario: Exactly one p-toast

- **WHEN** the application renders
- **THEN** exactly one `<p-toast>` element exists in the project

#### Scenario: p-toast in root layout with high baseZIndex

- **WHEN** `<p-toast>` is mounted in `AdminShellComponent`
- **THEN** it has no `key` (unless documented) and `[baseZIndex]` is set high enough to render above `p-dialog`

### Requirement: Animations provider registered

The admin application SHALL register `provideAnimations()` (or `provideAnimationsAsync()`) in `app.config.ts` so PrimeNG toasts animate.

#### Scenario: Animations provider present

- **WHEN** `app.config.ts` providers are inspected
- **THEN** `provideAnimations()` or `provideAnimationsAsync()` is present

### Requirement: NotificationService API

Components SHALL never inject `MessageService` directly. They SHALL use a root-provided `NotificationService` with `success(detail: string)`, `error(detail: string)`, `warn(detail: string)`, and `info(detail: string)`. Success toasts live 3000ms; error toasts live 5000ms. Summary text is generated by the service.

#### Scenario: Components use NotificationService, not MessageService

- **WHEN** a component shows a toast
- **THEN** it calls `NotificationService` and does not inject `MessageService`

#### Scenario: NotificationService toast lifetimes

- **WHEN** `success()` is called
- **THEN** the toast auto-clears after 3000ms
- **WHEN** `error()` is called
- **THEN** the toast auto-clears after 5000ms

### Requirement: CRUD success and error toasts

After every successful create, update, and delete, the user SHALL see a success notification. After a failure, the user SHALL see an error notification using the server's error message when available, otherwise a generic one. Messages are short, consistent, specific (for example "Product created", "Order updated", "Customer deleted") and kept in one message map.

#### Scenario: Every create/update/delete shows success toast

- **WHEN** a create, update, or delete request succeeds
- **THEN** the user sees a success toast specific to the entity and action

#### Scenario: Every failure shows error toast

- **WHEN** a create, update, or delete request fails
- **THEN** the user sees an error toast with the server message when available, otherwise a generic message

### Requirement: Notify before navigation

If a flow navigates after saving, the notification SHALL be called before `router.navigate`, so `takeUntilDestroyed` cannot cancel it.

#### Scenario: Notification precedes navigation

- **WHEN** a save flow navigates after completing
- **THEN** `NotificationService` is called before `router.navigate`

### Requirement: Every subscribe handles errors

Every `.subscribe()` SHALL have `next` and `error` callbacks, and the error callback SHALL notify the user.

#### Scenario: Subscribe error callbacks notify

- **WHEN** a `.subscribe()` is registered
- **THEN** it has both `next` and `error` callbacks, and `error` notifies the user

### Requirement: Single global HTTP error handling

Global HTTP errors (401, 403, 5xx, network failure) SHALL be handled once in the HTTP interceptor with an error notification. Components SHALL NOT duplicate the same toast for those cases. The interceptor handles global/network errors; components handle validation and business errors only.

#### Scenario: Interceptor notifies on global errors once

- **WHEN** an HTTP request fails with 401, 403, 5xx, or a network error
- **THEN** the interceptor shows exactly one error notification

#### Scenario: Components do not duplicate interceptor toasts

- **WHEN** a request fails with a global/network error already covered by the interceptor
- **THEN** the component does not show a duplicate toast for that error

### Requirement: No UI, route, or API contract changes

The change SHALL not alter UI layout, routes, or API contracts.

#### Scenario: Layout, routes, and API contracts unchanged

- **WHEN** comparing before and after the change
- **THEN** UI layout, routes, and API contracts are identical
